# 项目规范初始化

通过开发者讨论和项目事实生成规范，兼容不同语言、框架、运行平台与仓库规模。默认只创建或更新规范文件，保留已有项目的技术选择和开发者决策。

## 范围与独立性

- 本 skill 自包含：只依赖本目录内的模板和指引，不调用或要求加载其他 skill，不要求项目外的规则文件、仓库、网站或个人配置。
- 目标项目的 AGENTS.md 与规范 skills 禁止依赖项目外的内容；生成结果不得引用本初始化 skill、它的安装目录或模板源路径。
- skills 之间不得链接、导入、调用或要求预先加载对方，也不得通过共享文档或符号链接形成隐含依赖。每个 skill 的规范性支持文件放在自己的目录内；内部文件可以互相引用。
- 读取目标项目的源码、依赖清单、工具配置和 CI 是获取项目事实，不等于依赖外置规范。项目的软件依赖和正常构建工具不受上述规范文件边界限制。
- 不安装依赖，不配置格式化、Lint、测试、CI 或构建工具，不创建演示源码、可执行脚本或空目录，不修改用户数据和运行配置。
- `.gitignore` 中的 `/local/` 条目是可选配套改动：在文件清单中单独列明，并在本次请求已包含该改动时才实施；否则只报告缺口。
- 遵守用户本轮的目标和已有授权。只要求讨论时停留在方案；已要求生成且信息充分时继续写入，不增加逐文件确认流程。

## 了解项目并与开发者对齐

1. 确定目标项目根目录；多仓库或路径有歧义时先解决歧义。只读查看适用的现有 AGENTS.md、已有 skills、README、架构资料和 Git 状态，保护开发者未提交的修改。
2. 按需查看依赖清单、锁文件、工具链版本、格式与 Lint 配置、构建入口、CI 以及有代表性的源码和测试。不读取凭据或用户私有数据，不为收集信息运行安装、构建或付费请求。
3. 区分已证实的项目事实、开发者明确决策、待确认信息和建议。配置、文档与实现冲突时指出差异，不擅自把其中一项升级成项目要求。
4. 首次初始化应与开发者对齐以下信息；沿用对话中已经明确的答案，不重复询问。把识别出的结果带入问题，合并为一次简短讨论：
   - 项目类型、用途、运行平台和交付或部署形式。
   - 已确定或倾向的语言、框架、运行时、依赖管理和构建方式。
   - 会改变推荐的规模、协作、兼容性、数据、凭据、外部服务或付费调用约束。
5. 缺失信息会改变规范时先询问开发者，并可继续不依赖答案的只读分析；不要用超时、猜测或模板默认值代替回答。
6. 已有项目优先整理现有约定；空项目主动给出适配的主要推荐，有实质取舍时再给备选。说明选择依据和维护影响，不把某种语言、目录或工具推广为全部项目的默认要求。

规范语言沿用项目与开发者偏好，未指定时使用中文。推荐可以在讨论中解释来源，但最终规则必须在项目内完整表达，不能用外部链接代替执行要求。

## 设计文件与规则归属

先给出简短方案：已确认的项目类型与技术方案、拟创建或修改的文件、各文件适用范围、主要推荐和仍需回答的问题。用户已有明确生成指令且方案不引入新的技术选择或额外范围时，说明后直接执行。

按项目规模裁剪，不把模板数量当交付指标：

- 小型、单用途项目可以只生成精简 AGENTS.md，不为了拆分而创建空泛 skills。
- 常规项目可使用 `<project>-project-structure`、`<project>-code-style`、`<project>-testing` 三份项目全局规范。名称使用项目实际标识，保持小写连字符且不超过 64 字符。
- 多语言项目由项目代码规范 skill 在自己的 references 中按语言、框架或目录组织细则；各部分明确适用范围，不要求无关代码加载全部细节。
- 专项 skill 仅在实际需要且属于本次范围时创建，通过自身 description 表达触发场景，不把入口加入根 AGENTS.md。
- 优先更新已有合适文件，保留有效规则、手写内容和已确认决策。不得为套用布局批量移动、重命名或替换现有规范。发现已有跨 skill 或项目外依赖时，在本次授权范围内内聚必要规则；超出范围的列明缺口。

### AGENTS.md 必须精简

- 只放每次任务都需要知道的项目概况、必要环境、命令执行位置、少量关键约束和项目全局规范入口。
- 可链接作用于整个项目的结构、整体代码和验证规范；不得链接专用 skill、局部操作指引、功能目录、教程或非全局文档。详细命令和规则放入相应规范。
- 不列全量 skills，不复制规范正文，不记录历史、设计过程、任务进度或单次验证结果。
- 逐段检查是否确实需要在每次任务开始时加载；否则移入对应 skill 或删除。不设机械行数要求。
- 始终保留规范自包含、skills 互不依赖和临时文件位置的简短约束。小项目不拆 skills 时，将必要细则简明内联。

### 临时文件规则归属

详细规则属于项目结构规范；根 AGENTS.md 只保留一句始终生效的位置要求。

- Agent 临时脚本、一次性工具、日志、截图、调试输出和下载物统一放项目根 `local/`，按需创建，可使用任务子目录。
- 不得把临时文件写到源码、文档、规则目录或项目根的散落文件中；`local/` 可整体删除，不存需要保留或交付的内容。
- 源码、构建配置和正式文档不得引用或依赖 `local/`。长期工具进入项目正式工具目录，交付文件进入约定的交付位置。
- 测试用框架管理或系统隔离的临时目录并自行清理，不依赖仓库中的 `local/` 或真实用户存储。
- 框架既有的构建产物、受管缓存，以及用户明确指定的输出位置，沿用各自约定，不把它们强行迁入 `local/`。
- 查看忽略规则是否覆盖根 `local/`。未覆盖时按本 skill 的范围约束处理，不擅自修改 Git 索引或全局忽略配置。

## 生成规范

需要生成对应文件时读取本 skill 内的模板；模板是待改写的内容骨架，不是必须完整复制的规则清单：

| 目标 | 内部模板 |
| --- | --- |
| 精简根入口 | [AGENTS.template.md](assets/AGENTS.template.md) |
| 项目结构与 local 规范 | [project-structure.template.md](assets/project-structure.template.md) |
| 代码规范 | [code-style.template.md](assets/code-style.template.md) |
| 测试与交付验证规范 | [testing.template.md](assets/testing.template.md) |

生成时：

1. 替换模板变量，删除模板说明、编辑注释和无关章节，不留空表格、占位符或假定命令。空项目未具备的检查能力如实说明，不写成已经可运行。
2. 每个 skill 有有效的 name 和 description；description 表明真实适用任务与范围，不列其他 skill 的调用链。第一版输出 Markdown 规范即可，不额外生成工具脚本或 UI 元数据。
3. 用项目现有配置确定格式、命名、模块和检查约定。缺少配置时，采用已与开发者对齐的方案，并区分当前能力与建议后续建立的门禁。
4. 明确项目特有的目录职责、依赖方向、平台边界和不可逆约束。只加入与该项目相关的凭据、数据、兼容或计费要求，不照搬来源项目的业务名称、框架或路径。
5. 验证规则按变化范围逐步扩大；测试关注可观察行为，保持聚焦。避免无意义地重复全量测试，也不禁止调试、复现 bug 或阶段性验证。文档初始化本身无需执行项目构建和业务测试。
6. 使用可移植的项目内相对路径；skill 支持文件的引用限制在自身目录内。AGENTS.md 到项目全局规范的链接以目标项目为基准生成。

## 核对并交付

实际读取最终文件并检查：

- 环境、目录、命令和推荐的状态有依据；没有把拟议配置写成已完成能力。
- 根 AGENTS.md 足够精简，所有指引链接都面向项目全局，没有专用入口或外置依赖。
- 各 skill 独立，引用存在，按实际路径解析后仍在允许的目录内，没有跨 skill、绕行共享文档或项目外依赖。
- 模板变量、编辑说明和无关章节已经清除；名称、frontmatter、适用范围和语言一致。
- `local/` 的根入口约束与结构规范一致，测试隔离例外明确；忽略状态如实记录。
- 只改动本次规范文件和已包含在范围内的配套项，保留原有未提交修改；未修改用户数据、工具链或运行配置。

交付说明列出实际创建或更新的文件、主要约定、实际执行的核对及尚未具备的检查能力。未运行的项目检查写明未运行及原因，不把静态阅读当作运行验证。

再次执行时复查项目变化和开发者决策，只更新失效事实与缺失约定，不重复追加章节或重置手写内容。
